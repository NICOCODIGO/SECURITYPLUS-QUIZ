# Database

PostgreSQL is the system of record. DynamoDB holds one thing. Schema lives in
`server/src/main/resources/db/migration/V1__init.sql`.

## Rules

1. **Flyway owns the schema.** `ddl-auto=validate`; Hibernate never writes DDL.
2. **Never edit an applied migration.** Schema changes are a new `V<n>__*.sql`.
   *Exception:* the content seed is a **repeatable** migration — see below.
3. `gen_random_uuid()` is core Postgres 13+, so no extension is required. There is
   deliberately **no `citext`** — case-insensitive email uniqueness uses a `lower(email)`
   index instead, so the schema applies unchanged to a stock RDS instance.

## How content gets into the database

`server/src/main/resources/db/migration/R__seed_content.sql` (~865KB, **generated — never
edit by hand**) holds the whole question bank: 28 objectives, 444 questions, 1,776 choices.

```bash
node scripts/generate-seed.mjs          # regenerate after editing questions
node scripts/generate-seed.mjs --check  # fails if stale; runs in verify.sh and CI
```

Three deliberate choices:

- **Generated by Node, not Java.** The bank lives in JavaScript modules that Node can import
  directly. Parsing JS from the JVM would be the wrong tool by a wide margin.
- **Repeatable (`R__`), not versioned.** Flyway re-applies a repeatable migration whenever
  its checksum changes — exactly right for reference data that keeps being edited. Adding a
  question means regenerating this one file, not writing `V3`, `V4`, `V5`. Every statement
  is an upsert keyed on a natural key (`objectives.code`, `questions.legacy_hash`,
  `choices (question_id, position)`), so re-running is safe.
- **Questions that disappear are retired, never deleted.** `attempt_answers` reference them,
  and a retired question's history should survive. The generator emits a final `update ...
  set status = 'retired'` for any published hash no longer in the bank.

The generator **refuses to run** on a bank with a missing/unknown objective, a
`correctAnswer` out of range, fewer than two choices, or two questions with identical text
(which would collide on `legacy_hash` and silently merge their history).

`ContentSeedTests` then asserts the result landed correctly in Postgres — see
[backend.md](backend.md).

## Tables

### Content

**`objectives`** — `code` PK (`'1.2'`, `'4.6'`), `domain_number` (1–5), `title`. Seeded from
`secapp/src/components/data/examObjectives.js`.

**`questions`** — `id` uuid PK, `legacy_hash` unique, `text` unique, `difficulty`
(`Beginner`/`Intermediate`/`Advanced`), `objective_code` → `objectives`, `filed_domain`,
`explanation`, `status` (`draft`/`published`/`retired`), timestamps.

**`choices`** — `id` uuid PK, `question_id` → `questions` (cascade), `position` 0–9, `text`,
`is_correct`, `rationale`. Unique on `(question_id, position)`.

`rationale` is why this **wrong** choice is wrong. It is null on the correct choice, which is
covered by `questions.explanation` instead.

### People

**`users`** — `id` uuid PK, `email`, `password_hash`, `display_name`, `role`
(`USER`/`ADMIN`), timestamps. `display_name` is only ever shown back to its owner — there is
no public profile and no cross-user visibility anywhere in this schema.

**`refresh_tokens`** — `user_id` → `users` (cascade), `token_hash` unique, `expires_at`,
`revoked_at`, `user_agent`. Only the SHA-256 of a token is stored.

### Attempts

**`attempts`** — `id` uuid PK, `user_id` → `users` **nullable** (anonymous attempts), `type`
(`domain`/`mock`/`weakest`/`custom`), `score` 0–100, `questions_count`, `duration_seconds`,
`domain_title`, `server_graded`, `submitted_at`.

**`attempt_answers`** — PK `(attempt_id, position)`, `question_id` → `questions`
(set null), `chosen_choice_id` → `choices` (set null, null = left blank), `is_correct`.

`domainBreakdown` is **not stored**. It is derived by joining through `questions` →
`objectives`, so it can never drift from the answers it summarises.

`server_graded` records *how* the score was arrived at, not how much it is trusted — there is
no ranking here, so nobody gains by lying to their own dashboard. Mock exams run as a
server-held session and are scored there; practice quizzes are scored in the browser. The two
can cross: the app must keep working with the API off, so a mock taken offline comes back
client-scored. The flag is what tells those apart afterwards.

### Account state

**`daily_answers`** — PK `(user_id, answered_on)`, `question_id`, `choice_id`, `is_correct`,
`answered_at`. Deliberately separate from `attempts`: a one-question 0%/100% would swing the
weighted averages. **The streak is derived from these rows, never stored as a counter.**

**`flagged_questions`** — PK `(user_id, question_id)`, `created_at`.

**`custom_quiz_presets`** — `id` uuid PK, `user_id`, `name`, `config` jsonb. Unique on
`(user_id, name)`.

## Indexes (8)

| Index | Purpose |
|---|---|
| `questions_objective_idx` | partial, `status = 'published'` |
| `questions_difficulty_idx` | partial, `status = 'published'` |
| `choices_question_idx` | lookup by question |
| `choices_one_correct_idx` | **unique partial, `where is_correct`** — an invariant |
| `users_email_lower_idx` | **unique on `lower(email)`** — an invariant |
| `refresh_tokens_user_idx` | partial, `where revoked_at is null` |
| `attempts_user_time_idx` | `(user_id, submitted_at desc)` — every dashboard query |
| `attempt_answers_question_idx` | "how often is this question missed" |

## Two invariants the schema enforces, and one it can't

- **`choices_one_correct_idx`** allows *at most* one correct choice per question.
- **`users_email_lower_idx`** makes email uniqueness case-insensitive.

"**At least** one correct choice" cannot be expressed as an index. The importer and the
content-integrity test assert that half — don't assume the database is guarding it.

## `objective_code` vs `filed_domain`

A question's **`objective_code` is the source of truth** for which domain it belongs to.
`filed_domain` records the `quizData` array it was imported from.

For **147 of the 444** questions these differ. That is the bug the import fixes. Keeping both
means per-domain stats can describe content while the old filing stays visible for
comparison. **Don't reintroduce domain logic that trusts the filing.** See
[content.md](content.md) for the numbers.

## `legacy_hash`

The existing djb2 `hashQuestion` value from the front end. It exists solely so imported
localStorage history joins to the right row, since stored attempts reference questions by
text hash.

**Don't drop it, and don't make it the primary key.** The whole point of the uuid is that
editing a question's wording no longer retires its history.

## DynamoDB — one table

**`exam_sessions`** — PK `session_id`; attributes `user_id`, `question_ids[]`, `answers` map,
`type`, `created_at`, `expires_at` (**TTL**).

An in-progress exam is written on every answer, read only by its own id, never joined to
anything, and worthless once finished or abandoned. DynamoDB stores it as a single item and
the TTL attribute expires the leftovers for free, with no cleanup job to write or run.
Everything relational stays in Postgres.

Local dev runs `dynamodb-local` with `-inMemory`, so **sessions vanish on container
restart** — see [devops.md](devops.md).

## Browser key → table map

Phase 3 syncs these. Anonymous users keep using browser storage; an account mirrors it.

| Browser key (`secapp/src/components/data/`) | Postgres |
|---|---|
| `quiz_history` (`quizHistoryData.js`) | `attempts` + `attempt_answers` |
| `daily_question` (`dailyQuestion.js`) | `daily_answers` |
| `flagged_questions` (`questionPools.js`) | `flagged_questions` |
| custom quiz configs (`CustomQuizBuilder`) | `custom_quiz_presets` |
| `security_plus_progress` (`progressData.js`) | **no table yet** — the writer is unreachable |

`POST /me/import` merges local history by `(legacy_hash, submitted_at)` so a double import
can't duplicate.
